safety:
  - title: A terminal state is never walked back
    detail: >-
      The acceptance write happens only when no row exists, and a primary-key
      collision on that path is ignored rather than retried as an update. Three
      regression tests pin reversed arrival, duplicate key and a failing retry.
  - title: The model is bounded to three calls, and uses two
    detail: >-
      Selection and reasoning are one call each. Visit order and travel legs are
      computed from coordinates. The third call is held in reserve so a format
      violation upstream can be corrected once rather than failing the request.
  - title: The output is checked as a contract before anyone sees it
    detail: >-
      Visit order must be a permutation of the selected places, legs must
      connect end to end, and every coordinate must fall inside the country's
      latitude and longitude range. The same range check exists on both the
      gateway and the agent so the two cannot drift apart.
  - title: Any node's error short-circuits to the payload
    detail: >-
      A node that sets an error skips the rest of the graph and goes straight to
      building a payload. The publish node always runs, so a failed job emits a
      failure event rather than leaving the client polling a row that never
      changes.
  - title: A missing feed degrades rather than fails
    detail: >-
      An upstream that does not answer produces a warning on the itinerary, not
      a 5xx. A missing forecast should not take down a trip that has nothing to
      do with the weather.
  - title: Re-recommendation is capped at the day boundary
    detail: >-
      Three per itinerary per day, counted by a Redis Lua INCR and EXPIREAT that
      expires at midnight Korean time rather than on a rolling window, so the
      limit means what the person reading it thinks it means.
  - title: The rate-limit key cannot be chosen by the caller
    detail: >-
      The forwarded-address header is read only when the immediate peer falls
      inside a configured trusted-proxy range, and only the single-valued header
      the edge always overwrites is trusted.
  - title: Internal guards fail closed
    detail: >-
      The internal token is compared as bytes, so a non-ASCII header returns 403
      rather than raising and returning 500. Failure falls to the closed side.
  - title: The reuse cache never stores a failure
    detail: >-
      Only a successful recommendation enters the cache, a hit rewrites the
      current job id onto its copy, and background refresh runs on a bounded
      queue.
  - title: Coordinates stay out of the logs
    detail: >-
      Origin and destination were being written to the access log in plain text,
      and rejection responses quoted place names. Both were removed.
fixes:
  - title: A finished job walked backwards into "in progress"
    area: user · Java BFF
    symptom: >-
      A recommendation would complete, and the client would keep polling
      forever. The job row said in_progress for a job that had finished seconds
      earlier. It did not reproduce on demand.
    cause: >-
      The record of acceptance and the record of completion were writes to the
      same row from two different paths. When the completion event won the race
      to the database, the late acceptance write overwrote the terminal state.
    fix: >-
      The acceptance write only happens when no row exists, and a primary key
      collision on that path is ignored rather than retried as an update, so a
      terminal state is never walked back. Three regression tests pin the
      orderings that used to break it.
  - title: Forecast lookups asked for grids nothing was ever stored for
    area: hub · gateway
    symptom: >-
      Short-term forecasts came back empty for most districts. Asking for a
      district that did not exist returned data, because the miss fell through
      to a province-level path — the wrong query worked and the right one did not.
    cause: >-
      Forecasts accumulate only on the grid points the poller subscribes to, but
      lookups used the requesting district's own grid point. Only 19 of the 243
      district grid points coincide with a subscribed one.
    fix: >-
      Resolve to the nearest active grid inside the same province, never across
      a province line — Gapyeong is fourteen times closer to a Gangwon grid than
      to its own province's, and a plausible forecast from the wrong zone is
      worse than none. The rule is a pure function, pinned by tests, and both
      the forecast and the observation paths now call it.
  - title: The poller died silently and left the day empty
    area: hub · scheduler
    symptom: >-
      Whole release cycles arrived with no forecast stored. Because the work ran
      as a background task nobody awaited, the failure left no trace at all, and
      it recurred at the same point every cycle.
    cause: >-
      A database exception inside the per-grid loop escaped the loop, so the
      remaining grids for that release were never written. One value outside the
      accepted category set rolled back that grid's entire transaction.
    fix: >-
      Per-grid exception isolation, an explicit log when the task dies, category
      filtering before the write, one query to decide what is already stored
      instead of one per grid, and a duplicate guard that the boot-time run and
      a manual run can both see.
  - title: Two regional forecast codes were swapped
    area: hub · gateway
    symptom: >-
      Medium-range land forecasts for two southern regions were each returning
      the other's outlook. Every response was well formed, and the only way to
      see it was to know the weather.
    cause: >-
      The region-code table had the two identifiers transposed at the point they
      were seeded.
    fix: >-
      Corrected the mapping and covered the region table with tests, because a
      transposition inside valid-looking data is invisible to every check that
      only inspects shape.
  - title: The rate limiter let the caller choose its own counter
    area: user · Java BFF · edge proxy
    symptom: >-
      A caller could send the same endpoint as many requests as it liked. The
      limit was in place and simply never bound.
    cause: >-
      The filter read the forwarded-address header no matter who the immediate
      sender was, so the value that keys the counter was attacker-controlled. A
      comment said the edge made spoofing impossible; that assumption had been
      withdrawn some time earlier.
    fix: >-
      Read the header only when the immediate peer falls inside a configured
      trusted-proxy range, and read the single-valued header the edge always
      overwrites rather than the appendable one. Requests arriving from outside
      that range are keyed by their actual source address.
  - title: Long itineraries silently lost their road geometry
    area: user · Java BFF
    symptom: >-
      Itineraries above a certain size drew straight lines between every stop
      instead of following roads. Nothing surfaced in the interface; there was
      only a warning in the log.
    cause: >-
      The gateway accepts at most 20 legs per routing request and the BFF sent
      the whole itinerary in one batch, so anything over 22 stops was rejected
      in full and fell back to straight lines for every leg, not just the excess.
    fix: >-
      Chunk at 20 and recombine in the original leg order, so one rejected chunk
      costs only its own legs. Day-boundary legs are not requested at all, and
      the rejection response — which quoted place names and coordinates — was
      taken out of the log.
  - title: One database restart killed a run of recommendation jobs
    area: agent
    symptom: >-
      After the database came back, recommendation jobs failed consecutively, as
      many in a row as the pool held, then recovered on their own.
    cause: >-
      The checkpointer pool lent out connections severed by the restart. A dead
      connection was only detected when its first query failed, which is to say
      after the job had already claimed it.
    fix: >-
      Check the connection at the point it is borrowed. That adds one round trip
      per checkout, which a recommendation performs a handful of times.
  - title: An internal guard answered 500 where it should have answered 403
    area: hub · gateway
    symptom: >-
      A request carrying a non-ASCII internal token raised inside the guard and
      returned a server error instead of a refusal.
    cause: >-
      The token was compared as a string, and the comparison function raises on
      a non-ASCII operand.
    fix: >-
      Encode both sides to bytes before comparing, and refuse with 403 when the
      value is absent or different. An authentication failure has to fall to the
      closed side, not the error side.

import N from '../../components/note/N.astro';

MAP is a gateway with an agent behind it. Five external feeds — weather and air
quality, places and photos, blog reviews, subway and shared mobility, and the
road network — are polled on a schedule, cached and normalised behind one
service. A request for an itinerary is accepted immediately, planned on a
stream, and answered when it is done.<N id="map-ownership" />

The order is the design. A model asked to pick places from an open field invents
them; given a candidate list a deterministic engine has already filtered by
travel radius, weather and exclusion zones, the worst it can do is choose a bad
real place.<N id="map-llm-budget" /> Visit order and travel legs are not asked
for at all — they are computed from coordinates, exhaustively while that is
cheap.<N id="map-tsp" /> Of the agent's fourteen nodes, two call a
model.<N id="map-graph" />

The graph is written so that a failure anywhere in it still produces an answer.
Any node that sets an error skips the rest and goes straight to building a
payload, and the publish node always runs, so a failed job emits a failure event
rather than leaving a client polling a row that will never change. There are 981
automated tests behind that behaviour.<N id="map-test-count" />

The data side is where the defects were. Forecasts accumulate only on the grid
points the poller subscribes to, and the lookup path was asking for a different
set entirely, so most districts returned nothing while a malformed request
returned a usable answer.<N id="map-grid-coverage" /> The road-routing batch had
a ceiling the caller did not know about, and crossing it cost the whole
itinerary rather than the excess.<N id="map-batch-cap" />

In front of all of it: a Redis tier over a scheduled prefetch, so the external
feed is warm before anyone asks,<N id="map-cache-tiers" /> and a
re-recommendation cap that expires at midnight local time instead of on a
rolling window.<N id="map-rate-limit" />
