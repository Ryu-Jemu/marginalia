## 원천 데이터와 팀 내 기여

MAP은 날씨·장소·후기·교통 데이터를 저장된 여행 일정으로 연결합니다. 저는 **아키텍처 설계, AI·백엔드, 서비스 통합, GCP·NCP와 앱 심사 제출**을 담당했습니다. 디자인·프론트 초기 세팅은 팀원이 맡았으며 초기 인증·캐시·vision과 일부 앱 기능에도 팀원의 기여가 있습니다. 직접 구현한 내용과 후속 개선은 기여표에 구분했습니다.<N id="map-ownership" lang="ko" />

**현재 앱은 스토어 심사 제출 후 대기 중입니다.** 2026-09-20 기준이며 서명 빌드, 산출물 검사, 배포와 심사 제출까지 담당했습니다.<N id="map-store-review" lang="ko" />

## 입력 품질과 저장 데이터

**공급자 응답의 의미부터 구분했습니다.** 조회 실패와 정상적인 빈 검색을 나누고, KMA 페이지 총수를 저장 전에 검사했습니다. PM10이 없어도 유효한 PM2.5는 남깁니다. 테스트 데이터는 명시적 모드와 별도 캐시로 분리했습니다. Hub는 다른 출처의 유효한 결과를 유지하고, Agent는 검증된 후보가 없으면 분류된 실패를 반환합니다.<N id="map-provider-quality" lang="ko" />

**코스 출처·좌표·경로 정보를 공통 형태로 정규화했습니다.** PostGIS에 upsert하고 반경으로 조회합니다. 예보 조회는 요청 지역을 같은 광역의 구독 격자에 대응시킵니다. Redis L1과 PostgreSQL 사전 적재는 원천별 조회·신선도 요구에 맞춰 사용합니다.<N id="map-cache-tiers" lang="ko" />

## 비동기 상태와 개인별 결과

BFF가 작업을 접수하면 Agent가 Hub를 통해 데이터를 조회하고, Redis Streams 완료 이벤트가 BFF로 돌아와 저장됩니다. 저는 접수와 종료 결과의 쓰기 규칙을 분리해 뒤늦은 접수가 완료된 작업을 다시 진행 중으로 바꾸지 않도록 했습니다.<N id="map-terminal-state" lang="ko" />

**공유 결과는 생성 당시의 의미를 유지해야 합니다.** 회귀 검사에서 대기 사용자가 생성자의 개인 편집본을 받는 문제를 재현했습니다. 공유 조회를 불변 worker 원본으로 바꾸고, 생성자·실행 식별자도 암호화 본문과 함께 인증했습니다. 이 부가 인증 정보가 AAD입니다. 개인 편집본은 별도 경로로 다루고, DB에 대기 시한을 남겨 Redis 정보가 사라진 뒤에도 후속 조회에서 만료를 종결하도록 했습니다.

**2026-09-09 집중 실행**에서 회귀 93건을 통과했습니다. 실제 서비스·consumer·store 코드, H2와 암호화를 사용했으며 Redis 명령은 메모리 대역으로 대체했습니다.<N id="map-test-count" lang="ko" />

## 추천과 앱 계약

- **경로 계산** — 그래프는 후보 준비·선정·경로·시간표·완료를 연결합니다.<N id="map-graph" lang="ko" /> 일반 추천은 선정과 설명에 모델을 사용합니다. 지정 장소의 경로는 출처를 확인한 뒤 두 모델 호출을 생략하고, 명시적인 최적화 요청에만 순서를 바꿉니다.<N id="map-llm-budget" lang="ko" />
- **계정 한도** — 인증된 재탐색은 계정 단위로 집계하고 KST 자정에 만료합니다. Redis 카운터 오류는 fail-open입니다.<N id="map-rate-limit" lang="ko" />
- **앱 연동** — 서버 동의 revision과 오류 코드를 Flutter에 연결했습니다. 늦게 도착한 동의 응답은 현재 계정·철회 상태와 대조하며, 추천 실패는 재시도 가능 여부를 유지합니다. 채팅에서는 자신의 읽음 이벤트가 반복 조회를 만들지 않도록 수정했습니다.<N id="map-client-contract" lang="ko" />

## Export와 배포 검사
