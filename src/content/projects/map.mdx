The bug that taught me most on this project was a race I could not reproduce on
demand. A recommendation would finish, the client would keep waiting, and the
job row would say `in_progress` — for a job that had completed several seconds
earlier.<N id="map-terminal-state" />

The completion event was arriving before the record of the job that produced it.
Whichever write landed second won, and half the time that was the stale one. The
fix was to stop treating the two writes as ordered at all: the first record is
only written when no row exists, and a primary key collision on the completion
path is retried as an update. A terminal state, once written, is never walked
back. Three regression tests fix the orderings that used to break it.

The other decision worth defending is where the model sits. A recommendation
agent that queries travel APIs directly is a weekend's work and impossible to
bound. This one runs behind a deterministic rule engine — travel radius by mode,
indoor preference when it rains, exclusion zones as polyline intersections — and
the model only chooses among candidates that already
passed.<N id="map-llm-budget" /> Its output is then checked as a contract before
anything downstream sees it.

Visit order is solved exhaustively while that is cheap and approximately once it
is not.<N id="map-tsp" /> The gateway keeps a Redis tier in front of a scheduled
prefetch, and a failed upstream degrades to an empty result rather than a 5xx,
because a missing weather forecast should not take down an
itinerary.<N id="map-cache-tiers" />

What I have not done here matters as much. The agent has no tests and no
evaluation set.<N id="map-agent-tests" /> Auth in the Java BFF is still a
placeholder.<N id="map-bff-auth" /> And on the Flutter client I am one
contributor among several, not the owner.<N id="map-flutter" />
