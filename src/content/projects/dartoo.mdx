import N from '../../components/note/N.astro';

The ingestion pipeline looked healthy. Every request returned 200, every worker
reported success, and the disclosure table filled up on schedule. What it did
not do was publish the events the rest of the system was waiting
for.<N id="dartoo-publisher-gap" />

The failure had no log line. When RabbitMQ came up after the disclosure service,
`EventPublisher` set `self.enabled = False` and never reset it, so once the
broker recovered the publisher stayed switched off and discarded every event in
silence. The success responses were telling the truth about persistence and
nothing at all about delivery.

The fix was a lazy reconnect — keep the publisher enabled after a startup
failure and reconnect on first publish — plus exponential backoff, a guard
against concurrent connection attempts, and a warning log carrying the receipt
number, so that a discarded event can never again be
invisible.<N id="dartoo-e2e-parity" />

A second assumption failed the same way. A retry counter had written off a batch
of `NOT_READY` responses as permanent, so I re-fetched four of them a week
later.<N id="dartoo-not-ready-experiment" /> All four came back normally. The
status code was mixed rather than terminal, which made it a policy problem: a
three-stage backoff for the transient case, dead-letter isolation for the
genuinely permanent one.

What that pair of bugs changed is how I read a green pipeline. Both were silent,
both survived every success check in the system, and both were only visible by
counting the same thing in two places and finding the numbers
different.<N id="dartoo-test-count" />
