safety:
  - title: Delivery is idempotent by content hash
    detail: >-
      A sha256 key derived from the notification's own content makes a repeated
      event a no-op rather than a second push, so a redelivery after a consumer
      restart cannot reach a phone twice.
  - title: A failed message reaches the dead-letter queue
    detail: >-
      The consumer acknowledges on outcome, not on delivery, so a message that
      raises is negatively acknowledged and routed to the dead-letter exchange
      with a seven-day time to live — long enough to inspect and replay.
  - title: Transient and permanent upstream failures are separated
    detail: >-
      A staged backoff waits out documents the upstream has not published yet;

      instead of being retried into the daily API quota.
  - title: The publisher reconnects rather than switching itself off
    detail: >-

fixes:
  - title: The pipeline reported success while delivering nothing
    area: disclosure · ingestion
    symptom: >-
      Every request returned 200, every worker reported success, and the
      disclosure table filled up on schedule. 959 rows were persisted and only
      805 events reached the queue. No log line marked the other 154.
    cause: >-
      When the broker came up after the disclosure service, the publisher set
      its enabled flag to false and never reset it. Once the broker recovered
      the publisher stayed switched off and discarded every event silently.
    fix: >-
      A lazy reconnect on first publish, exponential backoff, a guard against
      concurrent connection attempts, and a warning carrying the receipt number
      so a discarded event can never be invisible again. The next end-to-end run
      produced 3,948 rows and 3,948 events.
  - title: A retry counter had decided the wrong thing was permanent
    area: ingestion
    symptom: >-
      Filings whose source document was not ready came back with the same
      status code whether they would be ready in a minute or never. A fixed
      retry ceiling wrote them all off, and the failure log grew.
    cause: >-
      The status code was mixed rather than terminal, so a counter could not
      separate the two cases. I re-fetched four filings that had been marked
      permanently failed a week earlier; all four returned normally.
    fix: >-
      A staged backoff with a delay tuned to how long the upstream actually
      takes to publish, dead-letter isolation for the genuinely permanent case,
      and a per-day call ceiling so retries cannot exhaust the API quota.
  - title: Source documents failed to parse on encoding alone
    area: ingestion
    symptom: >-
      Filing archives contained documents in cp949, euc-kr and utf-8, some with
      no charset declared at all. Parsing failed on those, and the failure
      looked like bad data rather than a decoding problem.
    cause: >-
      The normaliser trusted the declared charset, and legacy declarations such
      as ks_c_5601-1987 do not match any codec name Python knows.
    fix: >-
      Charset auto-detection for undeclared documents, a Korean codec priority
      list, alias normalisation, and stricter HTML charset extraction. The
      normaliser went from 105 lines to 566, and the parse failures stopped.
  - title: Failed messages were dropped instead of dead-lettered
    area: notification
    symptom: >-
      A message that raised during processing disappeared. The dead-letter queue
      stayed empty, so there was nothing to inspect and nothing to replay.
    cause: >-
      The consumer acknowledged on delivery rather than on outcome, so the
      broker considered a failed message handled.
    fix: >-
      Explicit acknowledge on success and negative-acknowledge on failure, which
      is what routes a message to the dead-letter exchange, plus a
      correlation id carried from the event into every log line so one delivery
      can be followed across four services.
  - title: The daily model-spend cap could stop applying
    area: summary
    symptom: >-
      The counter that limits how many documents get summarised per day would
      occasionally stop resetting, and then never allow another summary.
    cause: >-
      An increment followed by a separate expiry call can be interrupted between
      the two, leaving a counter with no expiry set.
    fix: >-
      One Lua script so both happen or neither, with the day boundary pinned to
      Asia/Seoul rather than the container's clock.
  - title: Model output arrived wrapped in a code fence
    area: summary
    symptom: >-
      Summary requests succeeded upstream and then failed to parse, so filings
      were stored without the summary the notification depended on.
    cause: >-
      The model returned valid JSON inside a fenced code block, and the parser
      was handed the fence along with it.
    fix: >-
      Unwrap before parsing, map the importance labels to the values the rest of
      the system uses, and add a mock mode so the whole path can be integration
      tested without paying per run.

import N from '../../components/note/N.astro';

Dartoo is a data pipeline with a phone on the end of it. Regulatory filings are
polled from the national disclosure system, their source archives decoded and
normalised, the text summarised, and the result pushed to whoever was watching
that company. I owned four of the services on that path.<N id="dartoo-ownership" />

The two defects worth showing were both silent. Neither appeared in a status
code, and both were only visible by counting the same thing in two places and
finding the numbers different.<N id="dartoo-publisher-gap" /> The publisher had
been switched off for an entire run while every request in front of it returned
200; reconciling persisted rows against published events was the only signal
that existed.<N id="dartoo-e2e-parity" />

The second was a classification error rather than a crash. A retry counter had
written off a batch of not-ready responses as permanent, so I re-fetched four of
them a week later and all four came back normally.<N id="dartoo-not-ready-experiment" />
That made it a policy problem rather than a bug: a staged backoff for the
transient case, dead-letter isolation for the permanent one.

The delivery path was rebuilt rather than adapted — an asynchronous consumer,
sha256 idempotency keys, a ten-step orchestration and a seven-day dead-letter
queue.<N id="dartoo-notification-scope" /> The spend cap on the summary service
is one Lua script for the same reason.<N id="dartoo-lua-scope" /> Across the
three services I owned there are 319 automated tests.<N id="dartoo-test-count" />
